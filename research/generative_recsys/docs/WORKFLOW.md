# Проект рабочего процесса для KION

Статус: проект реализации по литературе, 2026-10-25. Это наш план адаптации;
параметры ещё не проверены обучением. Литературная основа — [TIGER](https://arxiv.org/html/2305.05065v3)
и [GRID](https://arxiv.org/html/2507.22224v1); различия протокола описаны явно.

## 1. Зафиксировать задачу до выбора модели

Вход: история доступных user–item пар строго раньше cutoff. Выход: топ-10 новых
для пользователя фильмов. Метки: все наблюдаемые новые пары следующей недели,
как в baseline. Сохраняем исходные train dates и validation date, dev-user IDs,
метрику macro NDCG@10; test не участвует в разработке.

Первый генератор выдаёт вероятность **одного следующего интересного объекта**.
Для недельного target создаём несколько обучающих примеров с общей историей:
по одному на каждый positive недели. Нормируем суммарный вес запроса, чтобы
пользователи с многими positives не доминировали. Это выбранная адаптация,
а не оригинальный next-item протокол TIGER.

Декодируем несколько альтернатив одного SID через beam search и получаем топ
фильмов. Не добавляем уже сгенерированные рекомендации в историю как якобы
состоявшиеся просмотры: тогда получится другая модель условной выдачи.

## 2. Контракты стадий

| Стадия | Артефакт | Что проверяем до следующей стадии |
|---|---|---|
| Временные срезы | `queries`, `history`, `truth`, `catalog` | История раньше cutoff, стабильные ID и хеши |
| Тексты объектов | `items_text` + template/revision | Все item_id присутствуют, нет статистик будущих просмотров |
| Text encoder | `item_embeddings` + item order | Размеры, конечность, отсутствие пропущенных объектов |
| Tokenizer | centroids / checkpoint + config | Детерминизм, reconstruction, code usage |
| Коды | `item_to_sid`, `sid_to_item` | Однозначное восстановление, обработка коллизий |
| Генератор | weights + config + learning curves | Корректный shift targets, masks, loss на SID |
| Декодирование | `recommendations` + scores | Валидность, уникальность, unseen, достаточная длина |
| Оценка | metrics + per-user + timings | Те же пользователи и знаменатели, retrieval misses сохранены |

Каждый запуск получает отдельную папку, конфиги, source/data hashes и статус.
Артефакты нельзя переиспользовать по одному имени файла без проверки происхождения.

## 3. Каталог и временная доступность

В KION нет надёжного `published_at`. Для первого строгого режима предлагаем
каталог объектов, уже наблюдавшихся до cutoff. Это консервативный proxy доступности,
а не заявление о настоящем каталоге сервиса. Будущие positives вне такого каталога
считаем промахами; отдельно показываем их долю, не удаляем из truth.

Tokenizer fit — на объектах, известных к самому раннему train cutoff. Затем
замораживаем его и кодируем новые объекты без переобучения на validation/test.
Если новые объекты могут создавать коллизии, политика suffix должна поддерживать
добавление без перенумерации старых ID. Размеры codebooks, резерв для suffix и
поведение при переполнении фиксируются заранее; обнаруженный overflow не скрывать.
Дерево допустимых кодов обновляется только из каталога соответствующего cutoff.

Есть альтернативный transductive-режим: все метаданные считаем известными заранее.
Его можно исследовать отдельно, но доступность будущих объектов тогда является
явным допущением, а не результатом проверки без утечек.

Ограничение `last_watch_dt` сохраняется: прошлые повторные просмотры могли быть
затёрты последней датой пары. См. [аудит](../../../baseline/LEAKAGE_AUDIT.md).

## 4. Получить embeddings русского контента

Предлагаемый старт — замороженный `intfloat/multilingual-e5-small`, батчами,
с сохранённой revision. Формат текста сначала ограничить названием и полями
метаданных; затем отдельно добавить description. Авторская инструкция для
использования embeddings в clustering — `query: `; pooling и normalization
сверить с [model card](https://huggingface.co/intfloat/multilingual-e5-small?inference_provider=hf-inference).

Encoder нужен один раз для каталога, а не на каждом шаге generator training.
Не требуется обучать большую языковую модель. Русский язык и пригодность
текста для пользовательских интересов всё равно проверять абляцией.

Baseline пока не получает text embeddings. Поэтому сравнение с текстовым SID
добавляет новую информацию. Показать это отдельно: baseline с теми же content
embeddings, генератор с ID-only кодами и генератор с semantic codes. Предобученный
encoder также является внешним источником знаний; его нельзя назвать обученным
исключительно на нашем KION или гарантированно доступным в 2021 году.

## 5. Построить SID

Предлагаемый прототип: 3 уровня residual k-means, ширина 64 или 128 как стартовый
поиск; финальный collision discriminator при необходимости. Размер выбрать
по occupancy и downstream validation, не по максимальной теоретической ёмкости.
Эти значения — наши малые конфигурации, не рецепт из статьи.

Для каждого item SID должен восстанавливаться ровно в один item_id. Добавление
discriminator сохраняет семантический префикс, но не превращает последний токен
в семантическую категорию. Идентификаторы уровней различаем offsets или level
embeddings; `PAD/BOS/EOS/UNK` выделяем явно.

Логировать: ошибку реконструкции, число используемых кодов каждого уровня,
распределение их частот, число уникальных SID до/после collision handling,
максимальный размер collision bucket и устойчивость при повторном кодировании.
Связь подобных диагностик с рекомендациями обсуждается в
[FORGE](https://arxiv.org/html/2509.20904v3); на KION её нужно проверить.

Следом заменить только tokenizer на RQ-VAE: те же тексты, embeddings, запросы,
генератор и бюджет подбора. Иначе нельзя приписать эффект квантованию.

## 6. Обучить маленький encoder–decoder

Стартовая конфигурация: `d_model=128`, 2 encoder + 2 decoder blocks, 4 heads,
dropout 0.1, история до 64–128 объектов. Один объект занимает несколько SID
токенов: 128 объектов × 4 токена — уже 512 токенов, не последовательность длины 128.
Размер batch выбирать по измеренной VRAM RTX 2060; скорость заранее неизвестна.
Content encoder на этом этапе уже выгружен, embeddings закэшированы.

Teacher forcing предсказывает токены target SID только по истории и предыдущим
**токенам того же target**. Loss — сумма token CE; padding исключён. Target целиком
не должен попадать в encoder input. Каждый пользовательский запрос имеет единичный
суммарный вес независимо от числа его positives.

Критически важно: порядок объектов внутри дня неизвестен. Первый KION encoder
можно сделать перестановочно-эквивариантным по объектам одного дня: одинаковое
кодирование даты, отдельная позиция уровня внутри SID, без произвольного
внутридневного item-position. Decoder может читать весь известный past.
Это архитектурная адаптация, не точная реплика T5 с исходными positional biases.
Обязательный тест: перестановка целых SID-блоков внутри дня не меняет оценки.

Дополнительное pretraining на исторических префиксах — следующий режим, с labels
только до validation boundary. Не расширять supervision на всех пользователей
молча: это отдельный бюджет данных относительно baseline.

## 7. Получить top-K через constrained beam search

Строим trie **всех допустимых SID каталога**. Он задаёт разрешённые продолжения
кода, но не выбирает предварительно сотню фильмов по жанру/популярности.
На выходе проверяем SID→item, удаляем просмотренные, дубли и недоступные объекты.
Исключение seen лучше учитывать при поиске или расширять beam, пока хватает
допустимых результатов. При дефиците показываем фактическую длину списка;
не прячем популярностный fallback внутри метрик генератора.

Сначала задаём точный контракт оценки кода:

`score(item | history) = sum_j log p(sid_j | history, sid_<j)`.

Вероятности считаем по исходному распределению модели. Если после ограничения
разрешённых токенов делать локальную перенормировку, можно изменить порядок
полных кодов. Это допустимая другая модель поиска, но не незаметная деталь.
Для нашего контракта маскировать недопустимые продолжения после вычисления
исходных log probabilities; возвращённые библиотекой scores сверять с этим
определением. API prefix constraints описан в
[Transformers](https://huggingface.co/docs/transformers/main/en/internal/generation_utils#transformers.PrefixConstrainedLogitsProcessor).

Beam search не гарантирует точный top-K. На небольшом каталоге сначала
перебрать likelihood всех полных допустимых SID и сравнить с beam:
доля совпадения топов, потеря NDCG из-за поиска и latency. Изменение beam width
должно быть отдельным параметром в отчёте. Для кода фиксированной длины исключить
непреднамеренный length penalty. `num_beams` и число возвращённых фильмов
не обязательно одно и то же из-за фильтрации.

## 8. Оценить два разных утверждения

**Основной эксперимент — полные системы.** Общие query-users, cutoff, truth,
доступный каталог, фильтры seen и метрики; baseline retrieval+CatBoost против
генератора SID. Списки фактически рассмотренных объектов будут разными —
это честное сравнение систем, а не изолированное сравнение ранжировщиков.
Показываем candidate recall baseline и реальный top-K генератора.

**Контроль по требованию задания об одинаковых кандидатах.** На замороженном
списке baseline оценить каждый SID его полной вероятностью и отсортировать.
Это дополнительный диагностический режим, свободную генерацию он не заменяет.
Если сравнивать обе модели на полном каталоге, стоимость и candidate distribution
бустинга нужно учитывать отдельно; старую модель нельзя автоматически считать
адаптированной к новому режиму.

NDCG@10, Recall@10, MAP@10 — macro по тем же тёплым пользователям с positives,
включая промахи и неполные выдачи. Не сравнивать с цифрами next-item/leave-one-out
из статей напрямую. Логировать valid-ID rate, coverage, seen/duplicate rate,
latency генерации, peak VRAM/RAM и полное время стадий.

Validation — только для подбора. Уже просмотренную августовскую test-неделю
нельзя назвать новым независимым финальным тестом после дальнейшей разработки.

## 9. Минимальные проверки перед GPU-training

1. Каждый SID однозначно восстанавливается; сериализация не меняет mapping.
2. Future mutation не меняет past input, tokenizer или доступный каталог.
3. Нет `label`, будущего target или агрегированного watched_pct в encoder inputs.
4. Target-shift, PAD masking и перенос decoder cache проверены tiny-fixture.
5. Модель переобучается на маленьком наборе; loss падает и выученные SID генерируются.
6. Trie не пропускает отсутствующие коды; все branches/длина target тестируются.
7. Beam scores сверены с полным перебором и teacher-forced likelihood.
8. Метрики совпадают с существующим evaluator на фиксированных рекомендациях.
9. CPU smoke проходит каждую стадию и сохраняет logs/status/checkpoints.

После этих проверок — ограниченный GPU-run и затем полный эксперимент.

## 10. Порядок реализации

1. KION-adapter + временные контракты.
2. Text embeddings + residual k-means + SID audit.
3. Tiny encoder–decoder + exhaustive scoring.
4. Trie/beam + сравнение с exhaustive top-K.
5. Validation-run с логами.
6. Абляции random codes / semantic codes / RQ-VAE при общей архитектуре.
7. Следующие улучшения из LC-Rec/OneRec только после устойчивого первого результата.
