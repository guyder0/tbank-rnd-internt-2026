# KION: длина истории, разреженность и полезность пользователей Задача — оценить, сколько информации есть для персонализации, какую часть данных теряем при порогах активности и действительно ли пользователи с короткой историей снижают метрику. **Два разных вопроса:** пригодность пользователя для обучения ранжировщика и качество рекомендаций ему на оценке. Не имеющий достаточного сигнала train-query можно исключить из обучения; исключение пользователя из оценки меняет аудиторию и условную метрику. Для признаков и порогов используется только история **до 2021-08-09**. Полный архив показан отдельно как описание датасета, не как доступная модели история. Диагностика качества — по уже сохранённой validation существующей v2, текущие GPU-эксперименты не читаем. Holdout/test-метрики не открываем.

## 2. Плотность user–item матрицы `density = число уникальных наблюдаемых пар / (число пользователей × число объектов)`, `sparsity = 1 − density`. Это бинарная матрица взаимодействий; нули не означают отрицательный отклик. Два знаменателя: только объекты с наблюдаемыми взаимодействиями и весь каталог метаданных. Каталог не имеет времён публикации, поэтому знаменатель «весь каталог» — описательная величина, а не восстановленный доступный каталог на дату. Персональная плотность — `n_pairs / catalog_size`. Это **не KDE**: число просмотров дискретно и имеет длинный хвост. Для него ECDF и log-гистограмма интерпретируются надёжнее сглаженной непрерывной оценки плотности.

## 3. Цена минимального порога истории Сколько пользователей и наблюдаемых пар остаётся, если требовать минимум k объектов **на момент предсказания**. Пользователь с 3 объектами может быть слабым для индивидуальной персонализации, но его взаимодействия всё ещё полезны для глобальных item/co-view статистик. Поэтому отбор train-query не должен автоматически удалять его строки из глобальных агрегатов.

## 4. Действительно ли короткие истории снижают validation-метрику? Используем сохранённую **v2 на expanded-кандидатах**. Группы строятся только по числу прошлых объектов, а не по полному числу просмотров или будущей активности. Будущие положительные объекты нужны лишь для уже рассчитанной оценки. Метрика усредняется по пользователям с хотя бы одним новым объектом в следующей неделе. Поэтому состав этой группы отличается от всех 30 000. `candidate_recall` помогает отличать промах retrieval от плохой перестановки кандидатов. Малые сегменты имеют большую неопределённость; приведённый bootstrap условен на фиксированной модели и неделе. Дополнительно сравниваем с популярностью на тех же кандидатах. `oracle_ndcg@10` — потолок при идеальном ранжировании уже найденных кандидатов: все их положительные объекты стоят первыми. Это диагностика с известными метками, не вход модели. Разрыв до потолка относится к ранжированию, сам потолок ограничен retrieval. `ndcg_fraction_of_oracle` — отношение средних метрик сегмента, не вероятность успеха.

## 5. Что произойдёт с метрикой, если убрать короткие истории из оценки? Это **не новое обучение**: пересчитывается среднее тех же сохранённых предсказаний на подмножестве пользователей. Если NDCG изменится, это эффект состава аудитории, а не улучшение модели. Показываем также долю сохранённых пользователей и будущих положительных объектов. Фильтрация по числу просмотров во всём архиве была бы утечкой: часть событий случится после предсказания. Корректный порог основан только на прошлом своего cutoff.

## 6. Выводы и следующий эксперимент Порог полезности надо проверять экспериментом, не объявлять любой короткий профиль бесполезным. Для ранжировщика уже исключаются train-query без положительных кандидатов — они не дают pairwise-сигнала. Короткий сегмент легче и для популярности: при одном прошлом объекте popularity NDCG=0,19562, v2=0,22134. При >50 объектах: 0,02626 и 0,05356. Покрытие будущих объектов генератором кандидатов также ниже у активных: 32,72% против 64,26% для одного объекта.
